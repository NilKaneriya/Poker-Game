# Load test: 200 tables, 40 s, before the storage fix (2026-11-22)

Run before commit `6da1b00` ("perf(storage): batch JSON file writes"). The report option
did not exist yet; the console output below was copied from the run.
The same load after the fix: [2026-11-23-200t-60s.md](2026-11-23-200t-60s.md).

## Setup
| | |
|---|---|
| Server | throwaway server started by the test (JSON storage in a temp folder) |
| Tables | 200 bots tables x 6 seats = 200 players + 1,000 bots |
| Duration | 40 s of play after everyone joined |
| Timings | BOT_THINK_MS=150, NEXT_HAND_DELAY_MS=300, RESULT_SHOW_MS=300 (about 10x faster than real play) |
| Machine | Windows 11, Node v24.18.1 |

## Result
| Metric | Before the fix | After the fix (same load) |
|---|---|---|
| Hands per minute | 1,466 | 2,508 |
| Action -> new state p50 | 32.5 ms | 5.9 ms |
| Action -> new state p95 | 346.3 ms | 19.0 ms |
| Action -> new state p99 | 545.1 ms | 33.6 ms |
| Action -> new state max | 704.2 ms | 77.2 ms |
| Event-loop delay, worst p99 | 695 ms | 64 ms |
| Rejected actions / connection errors | 0 / 0 | 0 / 0 |

## What it showed
The server answered correctly (no errors, no rejected actions) but the event loop was
blocked for up to 0.7 s at a time, so some players waited half a second for their action
to show. Cause: every save rewrote the whole JSON file synchronously, and with 200
players x 30 saved hands the hand-history file is several MB, rewritten about 24 times
a second. Logged as [BUG-07](../../bugs.md#bug-07).
